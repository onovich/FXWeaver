# 面向游戏的 Shader／特效平台：产品判断

更新：2026-09-30。本文是产品策略假设；公开功能事实引用一手来源。竞品事实细目另见 [平台竞品核查](./game-shader-platform-competitors.md)。尚未做用户访谈、竞品完整上手测试或付费验证。

## 核心判断

“游戏版 Shadertoy”比单纯节点编辑器有更高的平台上限：创作、发现、改造、预览、导入项目、再分享形成循环。但平台的冷启动和持续运营成本也更高。不能以“Shader 作品库”“标签”“分享链接”“AI 可调用”本身为差异点；这些能力已有相邻供给。[Shadertoy 分享/嵌入示例](https://www.shadertoy.com/view/Mfd3W4) · [Godot Shaders 作品目录](https://godotshaders.com/shader/) · [Unity Asset Store VFX](https://assetstore.unity.com/vfx/shaders)

更具体的价值主张是：**平台中的每个作品都由同一套节点工具创作，分享时附带可编辑源图；使用者能换上自己的素材、调整或派生，并在指定游戏运行时可靠使用。** “游戏可用”应有可以检查的含义：输入要求、透明/坐标/色彩语义、资源依赖、作用范围、参数与动画、目标版本、已验证导出、性能条件、许可证及来源。

## 统一创作格式是产品核心

首批内容只发布团队自己通过编辑器创作并验证的作品。开放创作者后，公开作品仍必须以平台的版本化节点图为源文件。生成的 GLSL/WGSL/HLSL、材质配置、运行时组件和引擎项目包是从源图构建的交付物。这形成比普通作品目录更强的保证：每个作品可在同一编辑器打开、修改参数、查看依赖、派生并重新导出。

这是一套**平台内部的资产标准**，不是跨引擎统一 Shader 规范。节点图可复用数学与纹理处理节点，但 Sprite 材质、对象滤镜、全屏后效和粒子系统需要不同的输入、输出和运行时配方。尤其粒子系统还有发射、模拟、生命周期和排序；不应把它假装成一个片元着色器。导出到 Unity 并不意味着导出的包会变成 Unity 原生 Shader Graph；源图仍在本平台编辑，除非另行开发原生图导出器。

因此首版应固定一种图类型、一个目标运行时及其版本。建议先做 2D Web 的 Sprite／Container 效果，明确宿主 API、色彩空间、透明语义和 WebGL 后端；全屏后效、Unity URP、Godot、粒子逐一增加。每增加一个目标，都要有真实示例项目中的编译、渲染和参数控制验证。页面上的“已验证”应写明目标版本、后端、测试场景与日期。性能描述应给出 Pass 数、采样量、渲染区域和设备条件，不能给一个脱离运行场景的统一分数。

## 竞品现实

- **Shadertoy**已经是创作、浏览、分享与嵌入 Shader 的社区，且有统一的创作接口。其公开作品示例使用 `iResolution`、`iTime`、`iChannel` 等环境变量；这一接口面向演示沙盒，与游戏引擎中的 Sprite、材质、相机后效并不自动等价。尚无依据量化“多数作品不能导入游戏”；稳妥的判断是很多作品需要输入、坐标、资源、性能和宿主代码适配。[Shadertoy 官方示例](https://www.shadertoy.com/view/Mfd3W4)
- **Godot Shaders**已经面向游戏，支持上传、搜索、类型、标签和许可过滤；部分作品还提供用法、实时预览或示例包。Godot 自身有统一的 Shader 语言，但作品涵盖 `canvas_item`、`spatial`、`particles` 等不同类型，社区作品不以统一的可编辑节点图和参数模型为前提。[Godot Shader 参考](https://docs.godotengine.org/en/stable/tutorials/shaders/shader_reference/) · [官方目录](https://godotshaders.com/shader/) · [作品示例](https://godotshaders.com/shader/2d-dissolve-with-burn-edge/)
- **Material Maker**也把节点编辑器与社区库连起来，作者可以发布材料、自定义节点及许可信息，使用者能在编辑器内导入。[社区文档](https://www.materialmaker.org/doc)
- **Unity Asset Store**有 Shader、粒子、全屏效果等资产类别和商业发布渠道；它是不同作者与实现方式的市场，不提供一套所有 Shader 必须遵循的可编辑图格式。Unity 官方也明确指出部分为 Built-in 管线制作的着色器和材质不能直接用于 URP／HDRP，需迁移或重建。[Unity Asset Store](https://assetstore.unity.com/vfx/shaders) · [Unity 管线迁移说明](https://docs.unity3d.com/ru/2020.2/Manual/BestPracticeMakingBelievableVisuals0.html)
- **NixieFX**已经提供浏览器创作、粒子材质图、时间线、目标运行时预览、后端支持报告，以及 CLI 和 AI agent skills；因此“节点 + VFX + 兼容性报告 + AI 可操作”也不是空白。[NixieFX 编辑器手册](https://nixiefx.com/editor-manual/) · [CLI](https://nixiefx.com/cli-reference/) · [Skills](https://nixiefx.com/skills/)

## 分类采用多个维度

用户提出的类别很有价值，但不能放在同一级互斥目录里。“粒子特效”是系统类型，“后效”是渲染位置，“转场”是用途，“像素风”是美术风格。建议每个作品用以下维度描述：

| 维度 | 示例 | 对使用者的作用 |
| --- | --- | --- |
| **运行位置 / 资产类型** | Sprite 材质、对象/图层滤镜、全屏后效、粒子系统、转场配方、3D 表面材质 | 决定输入、预览与导出器 |
| **游戏用途** | 受击反馈、技能、环境、UI、场景切换、状态效果 | 用任务语言搜索 |
| **视觉风格** | 像素风、卡通、写实、赛博、低多边形 | 用审美筛选 |
| **技术要求** | PixiJS 8 WebGL、Unity URP 版本、Godot 4；场景颜色/深度/法线；单 Pass/多 Pass；移动端档位 | 排除无法使用的效果 |
| **交付与许可** | 源图/代码/运行时包、资源清单、商业使用许可、可否修改/再发布 | 支持真实项目采用与二次创作 |

其中“粒子系统”和“风格化渲染”常超出单个片元 Shader：还可能有发射器、时间线、灯光、深度、多个渲染 Pass。平台可以收录多种资产，但初期不能承诺一个节点画布编辑所有类型。

## AI 易操作：先设计可编程资产，再接 MCP

MCP 官方规范允许服务器暴露有输入/输出 Schema 的工具、资源和提示词；它是连接方式，本身不会让 Shader 图变得可理解。[MCP Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) · [Resources](https://modelcontextprotocol.io/specification/2025-11-25/server/resources)

平台的核心应是稳定、版本化、可序列化的效果模型：带类型的节点与端口、明确的作用范围、语义参数、输入资源、目标能力和可重复的预览场景。浏览器 UI、CLI、REST API 和 MCP 都调用同一套操作。给 AI 的关键能力是闭环，而非只暴露“创建节点”：

1. `search_effects`：按用途、风格、宿主、许可证和成本查找。
2. `get_effect` / `fork_effect`：读取来源、依赖、参数、可修改源图与目标支持情况。
3. `set_parameters` / `edit_graph`：用结构化补丁修改草稿，稳定节点 ID，返回具体校验错误。
4. `render_preview`：在指定素材、分辨率、时间点输出截图与诊断。
5. `validate_target`：编译目标版本、运行示例、生成差异与限制报告。
6. `export_package`：返回可导入包、安装步骤和参数 API。

首版 MCP 可先提供搜索、读取、派生、调参、预览、导出；图结构编辑要等 Schema 稳定。发布共享作品涉及署名和许可，应有身份、权限与审阅流程。AI 产生的代码也需在受限预览环境中编译和渲染，避免单个作品拖垮服务。

作品来源也要从一开始治理。Godot Shaders 的许可说明区分 shader 代码与封面图、视频等资产的授权范围；Shadertoy 的统一许可和再分发规则在这次核查中未确认。首批内容只发布自己原创的作品；开放创作者后再增加投稿协议、授权声明和审阅，不能默认搬运其他社区作品。[Godot Shaders 许可说明](https://godotshaders.com/license/)

## 推荐启动顺序

1. **固定源图格式和首个运行位置**：选定 2D Web 游戏中的一种效果宿主和一个明确运行时版本，建立带类型的节点、参数、输入资源、图版本和构建器。让每个效果都能在编辑器内复现。
2. **只发布自己创作的标杆效果**：每个作品都提供源图、自己的素材预览、参数说明、目标导入包、真实项目验证记录和许可。展示“换素材→调参→看效果→下载包”的完整路径。
3. **让使用者派生和带回项目**：开放 fork、版本来源链和私人草稿，记录从换素材到导入成功的转化；API 与 UI 共用同一资产模型，再接搜索、读取、调参、预览、导出的 MCP 工具。
4. **图格式和审核稳定后开放创作者**：投稿只能从本编辑器的源图发布，自动校验输入、导出和预览，再人工检查质量、许可及内容；可先邀请制。
5. **增加第二目标与更多资产类型**：逐个加入引擎和渲染位置。粒子与风格化渲染作为新资产模式，不强行套进单个 Shader 图。重复使用和创作者供给得到验证后，再试付费效果包、团队库或交易市场。

## 需要验证的假设和停线信号

- **需求侧**：用户是否为“项目可用且能改的效果”而返回，而不只是浏览漂亮演示？看换自己的素材、修改参数、派生源图、导入成功、项目中保留及重复使用。若多数人只下载成品，节点图仍可作为内部生产工具，但社区侧的编辑优势需要重估。
- **供给侧**：创作者是否愿意维护版本、依赖、预览场景和许可？若投稿多而可用资产少，平台应转向精选发行或工具服务。
- **AI 侧**：代理能否通过工具在自己的项目里完成查找→调参→预览→导入？只做到搜索或生成 GLSL，不构成闭环优势。
- **跨引擎**：若第二目标需要大量人工重写，明确把作品标为宿主专用，不宣传无损跨引擎。

战略上宜保留一个平台，同时将“创作工具、作品目录、目标适配器、MCP”作为分层能力。首发应聚焦一个有真实使用场景的细分领域；将来用户群和工作流明显分化时，再考虑拆分 3D 材质、粒子 VFX 或交易市场。
